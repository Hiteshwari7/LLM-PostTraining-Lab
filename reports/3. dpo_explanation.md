# DPO (Direct Preference Optimization), Explained

## 1. The problem DPO solves

After SFT, a model produces *plausible* answers but "plausible" and "the answer a person would actually prefer" aren't the same thing. Two responses can both be factually fine while differing in conciseness, tone, or how directly they answer the question. SFT alone has no mechanism to learn *that kind* of preference, because its training data is just "correct answer," not "this answer over that one."

## 2. The classical answer: RLHF (PPO)

The original approach (used for models like the early ChatGPT) is Reinforcement Learning from Human Feedback:

1. Collect human preference judgments (A vs. B, which is better).
2. Train a separate **reward model** to predict those preference scores.
3. Use **PPO** (a reinforcement learning algorithm) to fine-tune the language model to maximize the reward model's score, while a KL penalty keeps it from drifting too far from the original SFT model.

This works, but it's a lot of moving parts: a reward model, an RL training loop, careful tuning of the KL penalty, and RL's usual instability.

## 3. DPO's shortcut

**Core insight:** the RLHF objective has a closed-form solution that lets you skip the reward model and the RL loop entirely. DPO reformulates the *same underlying goal* as a single, simple supervised-style loss computed directly from `(prompt, chosen, rejected)` triples:

- Increase the model's log-probability of `chosen` relative to `rejected`, relative to how a frozen **reference model** would have scored them.
- No reward model. No PPO rollouts. No RL instability — just a loss function and standard gradient descent, similar in spirit to how SFT is trained.

That's why this project uses DPO instead of full RLHF/PPO: it gets a comparable effect (aligning the model with preference data) with a training loop that's realistic to run end-to-end in a Colab notebook.

## 4. Key parameters (as used in this project's notebook/script)

| Parameter | This project's value | What it controls |
|---|---|---|
| `beta` | 0.1 | How strongly the model is pushed toward the preferred response vs. staying close to the reference (SFT) model. Lower `beta` = more aggressive preference updates; higher `beta` = more conservative. |
| `learning_rate` | 5e-6 | Deliberately much lower than SFT's `2e-4` — DPO is refining an already-good model's preferences, and a large step here quickly destabilizes fluency. |
| `num_train_epochs` | 2 | Preference datasets are usually small and hand-curated; too many passes risks overfitting to the exact chosen/rejected pairs rather than learning the general pattern. |
| `ref_model` | `None` (PEFT model) | With a LoRA/PEFT model, TRL can use the *same* base model with the adapter disabled as the implicit reference model — no need to keep a second full model copy in memory. |

## 5. What "the reference model" is doing

DPO doesn't just push the model toward `chosen` in an unconstrained way — every update is measured *relative to* what the reference model (here, the SFT checkpoint) would have predicted. This is what keeps the DPO model from drifting into degenerate behavior (e.g., always producing the same short "safe" answer) purely to satisfy the preference signal — `beta` is the dial that controls how tightly this constraint is enforced.

## 6. What to look for after training

In `03_Evaluation.ipynb`'s comparison table, DPO's effect is usually visible as: more direct answers, less hedging/repetition, and closer alignment with whatever pattern your `chosen` responses consistently had (e.g., if your chosen responses were shorter and more precise than the rejected ones, expect the DPO model's answers to trend that way too — see `results_analysis.md` once you've run it).
